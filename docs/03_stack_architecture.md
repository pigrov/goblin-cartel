# Goblin Cartel: стек и архитектура

**Версия:** 0.1  
**Дата:** 2026-04-28

## 1. Зафиксированное решение

Проект должен состоять из трёх частей:

1. **Android-приложение** — основная пользовательская версия, первая публикация в RuStore.
2. **Web-версия игры** — тот же игровой клиент, запускаемый в браузере для разработки, тестов и демо.
3. **Админка** — отдельное web-приложение для настройки контента, генерации уровней, баланса, версий конфигов и LiveOps.

Рекомендуемый стек для клиента:

```text
Vite + React + TypeScript + PixiJS + Capacitor
```

Рекомендуемый стек для backend/admin:

```text
Backend: Node.js + TypeScript + Fastify/NestJS
DB: PostgreSQL
Cache/queue later: Redis
Admin UI: React + Vite
Content validation: JSON Schema / Zod
Analytics later: own events table + external analytics adapter
```

## 2. Почему не Next.js для клиента

Next.js можно использовать, но для игрового клиента он избыточен. Игра должна быть client-side, статической и легко упаковываться в Android WebView. Vite производит production bundle, который подходит для статического хостинга и для копирования в Capacitor `webDir`.

Next.js можно оставить для:

- лендинга;
- документации;
- маркетингового сайта;
- возможно, админки, если потребуется SSR/роутинг/серверная часть.

Для самой игры лучше проще:

```text
Vite app → dist/ → Capacitor → Android APK/AAB
```

## 3. Роли технологий

| Технология | Роль |
|---|---|
| TypeScript | единый язык для клиента, game-core, админки и backend |
| Vite | сборка web-клиента и админки |
| React | UI: панели, карточки, меню, админка |
| PixiJS | 2D-сцена шахты, блоки, гоблины, частицы, тапы |
| Capacitor | Android wrapper, доступ к Android runtime, сборка для RuStore |
| PostgreSQL | хранение контента, версий, игроков, телеметрии |
| Zod/JSON Schema | валидация конфигов и данных админки |
| Zustand/Redux Toolkit | состояние клиента, если потребуется структурировать store |
| IndexedDB/localStorage | локальные сохранения MVP |

## 5. Разделение клиента

### 5.1. game-core

Чистая TypeScript-логика без React и PixiJS.

Отвечает за:

- расчёт урона по блокам;
- генерацию рудников;
- награды;
- экономику;
- производство;
- автоматизацию;
- офлайн-прогресс;
- апгрейды;
- сохранения;
- симуляции баланса.

Важно: game-core должен быть пригоден для запуска в тестах и в админском симуляторе.

### 5.2. React UI

Отвечает за:

- верхнюю панель ресурсов;
- нижнюю навигацию;
- карточки гоблинов;
- экраны шахт;
- экран автоматизации;
- popup-окна;
- настройки;
- локализацию;
- визуальные состояния кнопок.

### 5.3. PixiJS scene

Отвечает за:

- рендеринг шахты;
- блоки;
- гоблинов на платформе;
- частицы;
- всплывающие ресурсы;
- touch/click hit detection по блокам;
- эффекты разрушения;
- простые анимации.

## 7. Клиент: данные и состояние

### 7.1. Локальное состояние

Для MVP:

- game state хранится локально;
- сохранение через IndexedDB или localStorage;
- офлайн-прогресс считается при запуске по `lastSavedAt`;
- контент-конфиг встроен в билд или загружается с сервера.

### 7.2. Позже

- серверное сохранение игрока;
- cloud sync;
- защита от грубого tampering;
- события и LiveOps с сервера;
- сегментация игроков;
- аналитика.

## 8. Админка

Админка нужна не “когда-нибудь”, а уже для нормальной разработки MVP. Иначе каждый новый рудник будет правиться в коде, а это путь к священному хаосу.

Админка должна управлять:

- типами блоков;
- шаблонами рудников;
- правилами генерации;
- ресурсами;
- гоблинами;
- шахтами;
- автоматизациями;
- рецептами;
- экономическими коэффициентами;
- заданиями;
- текстами;
- публикацией версий конфигов.

Подробнее: `04_admin_cms_and_generation.md`.

## 9. Android через Capacitor

### 9.1. Dev workflow

```text
npm run dev
```

Запуск web-версии в браузере для основной разработки.

### 9.2. Android build workflow

```text
npm run build
npx cap sync android
npx cap run android
```

### 9.3. RuStore build

Для RuStore потребуется:

```text
vite build → cap sync android → Android/Gradle build → signed APK/AAB → загрузка в RuStore
```

Подробный чеклист: `06_rustore_release_plan.md`.

## 10. Web-версия

Web-версия нужна для:

- быстрого тестирования;
- QA;
- демонстраций;
- проверки баланса;
- возможной публикации web demo;
- подключения админского preview.

Важно: web-версия и Android-версия должны использовать один и тот же game-core и одни и те же конфиги.

## 11. Backend

### 11.1. MVP backend

В самом первом техническом MVP backend можно не делать, если контент встроен локально. Но для админки и генерации уровней backend всё равно понадобится рано.

Минимальный backend:

- авторизация админов;
- CRUD контентных сущностей;
- генерация рудника по шаблону;
- валидация конфига;
- публикация версии конфига;
- выдача клиенту активной версии конфига.

### 11.2. После MVP

- аккаунты игроков;
- сохранения;
- аналитика;
- события;
- A/B-тесты;
- управление RuStore-сборками;
- интеграция платежей;
- интеграция пушей.

## 12. Content delivery

Варианты:

### Вариант A: конфиги внутри клиента

Плюсы:

- проще;
- работает offline;
- меньше серверной зависимости.

Минусы:

- каждое изменение требует новой сборки.

### Вариант B: конфиги с backend/CDN

Плюсы:

- можно обновлять баланс без новой сборки;
- удобно для событий;
- удобно для A/B.

Минусы:

- нужна версия контента;
- нужна миграция сохранений;
- нужна защита от несовместимости.

### Рекомендация

Для MVP:

```text
локальный базовый конфиг + возможность загрузить remote config
```

То есть игра должна запускаться без сети, но при наличии сети подтягивать опубликованную версию конфига.

## 13. Сохранения

### MVP

```json
{
  "saveVersion": 1,
  "contentVersion": "0.1.0",
  "playerId": "local",
  "lastSavedAt": 1777370000000,
  "resources": {},
  "mineProgress": {},
  "goblins": [],
  "builtMines": [],
  "automation": []
}
```

### Важные правила

1. Каждое сохранение имеет `saveVersion`.
2. Каждая версия контента имеет `contentVersion`.
3. Нужны миграции сохранений.
4. Офлайн-прогресс считается ограниченно, чтобы игрок не получал бесконечные ресурсы из-за перевода часов.

## 14. Аналитика

MVP-события:

| Event | Когда отправляется |
|---|---|
| `game_start` | старт приложения |
| `mine_started` | открыт рудник |
| `block_destroyed` | разрушен блок |
| `vein_found` | найдена жила |
| `mine_built` | построена шахта |
| `resource_collected` | собран доход |
| `automation_unlocked` | куплена автоматизация |
| `goblin_hired` | нанят гоблин |
| `offline_reward_claimed` | получена офлайн-награда |

Не надо логировать каждый тап на сервер. Серверы тоже хотят жить.

## 15. Безопасность и античит

Для single-player idle в MVP не нужна тяжёлая античит-система.

Нужно:

- не доверять клиенту в будущих лидербордах;
- не вводить PvP/рейтинги до серверных проверок;
- ограничивать офлайн-прогресс;
- сохранять ключевые данные с checksum;
- при серверном sync валидировать невозможные скачки ресурсов.

## 16. Производительность

### PixiJS

- использовать atlas/spritesheet;
- батчить однотипные блоки;
- не создавать/удалять сотни объектов каждый кадр;
- переиспользовать частицы;
- ограничить видимую область шахты;
- снижать количество эффектов на слабых устройствах.

### React

- не ререндерить весь UI на каждый тик добычи;
- агрегировать обновления;
- использовать selectors в store;
- отделить game loop от React render loop.
