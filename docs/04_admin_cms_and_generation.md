# Goblin Cartel: админка, уровни, генерация и управление контентом

**Версия:** 0.1  
**Дата:** 2026-04-28

## 1. Зачем нужна админка

Idle-игра живёт на контенте, числах и регулярных правках баланса. Если всё забито в коде, каждое изменение превращается в маленький релизный кошмар, где “поменять HP камня” внезапно требует сборки, теста, публикации и тихого проклятия человечества.

Админка нужна для:

- создания рудников;
- генерации уровней;
- настройки блоков;
- настройки гоблинов;
- настройки шахт и производства;
- настройки автоматизации;
- баланса экономики;
- симуляции прогресса;
- публикации версий контента;
- подготовки событий и будущего LiveOps.

### 3.2. BlockType

Тип блока в руднике.

Поля:

| Поле | Описание |
|---|---|

## 4. Генерация рудников

## 4.1. Базовая идея

Рудник генерируется из шаблона:

```text
MineTemplate.cellMap + contentVersion → конкретная сетка блоков
```

Генерация должна быть детерминированной. Если есть `seed`, одна и та же версия шаблона должна давать один и тот же рудник. Это сильно упрощает тестирование и отладку, а значит чуть снижает шанс, что разработчик будет разговаривать с монитором.

## 4.2. Процесс генерации

```text
1. Выбрать шаблон рудника.
2. Создать seed.
3. Разбить рудник на страты/слои.
4. Для каждого блока выбрать тип по весам.
5. Разместить гарантированные объекты.
6. Разместить жилы по правилам.
7. Разместить сундуки и редкие объекты.
8. Проверить валидатором.
9. Прогнать симуляцию.
10. Сохранить preview и опубликовать.
```

## 4.3. Cell map / карта клеток

Слои нужны, чтобы рудник менялся по глубине.

Пример:

| Слой | Глубина | Блоки |
|---|---|---|
| Верхний грунт | 0-20м | земля, камень, золото |
| Каменный слой | 20-50м | камень, твёрдый камень, медь |
| Медный слой | 50-80м | камень, медь, сундуки |
| Нижний пласт | 80-120м | твёрдый камень, железо, хлам |

## 4.4. Веса блоков

В каждом слое задаются веса:

```json
{
  "stone": 60,
  "dirt": 20,
  "copper_ore": 15,
  "gold": 4,
  "chest": 1
}
```

## 4.5. Гарантированные объекты

Чтобы рудник не получился бессмысленным, важные вещи должны быть гарантированы:

- минимум 1 жила для обучения;
- минимум 1 сундук после 30% прогресса;
- минимум N медных блоков в медном руднике;
- финальная награда на дне.

## 4.6. Валидация рудника

Перед публикацией админка должна проверять:

| Проверка | Зачем |
|---|---|
| Есть ли достижимая цель | игрок не должен застрять |
| Есть ли гарантированная жила | иначе нет постройки шахты |
| Среднее время прохождения | чтобы рудник не был слишком долгим |
| Награды не ломают экономику | чтобы не выдать миллион меди на 5-й минуте |
| HP блоков соответствует прогрессии | чтобы не было стены сложности |
| Все assetId существуют | чтобы не получить пустой квадрат позора |
| Все локализационные ключи есть | чтобы не видеть `MINE_NAME_404` |

## 5. Симулятор баланса

Админка должна уметь прогнать рудник как бот.

Параметры симуляции:

| Параметр | Описание |
|---|---|
| `sessionLengthMin` | длительность активной сессии |
| `tapRate` | сколько ударов босса в минуту |
| `offlineHours` | сколько игрок был офлайн |
| `goblinSetup` | набор гоблинов |
| `automationSetup` | купленная автоматизация |
| `targetMine` | рудник |

Результаты:

- время прохождения;
- ресурсы в час;
- bottleneck-ресурс;
- количество ручных действий;
- момент покупки автоматизации;
- прогноз первого часа;
- прогноз первого дня.

## 6. Версионирование контента

Каждый опубликованный набор конфигов должен иметь версию:

```text
contentVersion: 0.1.0
status: draft / validated / published / archived
```

Правила:

1. Черновик можно менять.
2. Published-версию менять нельзя, только клонировать.
3. У клиента есть активная версия.
4. У сохранения игрока есть версия контента.
5. Нужны миграции, если структура меняется.

## 7. Процесс публикации контента

```text
Редактор меняет сущности
↓
Сохраняет draft
↓
Админка запускает валидацию
↓
Админка запускает симуляцию
↓
QA открывает preview
↓
Контент публикуется как новая версия
↓
Клиент получает config manifest
↓
Клиент загружает новую версию или использует локальную
```

## 12. Важные UX-детали админки

1. В редакторе рудника должен быть визуальный preview.
2. Каждое изменение должно показывать diff.
3. Нельзя публиковать конфиг с ошибками.
4. Симулятор должен показывать “первый час игрока”.
5. Нужен быстрый экспорт JSON.
6. Нужен импорт JSON для ручной правки.
7. Нужна история изменений.
8. Нужны комментарии QA к версии.

## 13. Самогенерация уровней

Есть два варианта.

### Вариант A: шаблонная генерация

Дизайнер задаёт правила, генератор создаёт рудник.

Плюсы:

- управляемо;
- легко валидировать;
- хорошо для MVP.

Минусы:

- меньше неожиданности.

### Вариант B: процедурные рудники по регионам

Игроки получают разные рудники на базе seed.

Плюсы:

- больше вариативности;
- легче масштабировать.

Минусы:

- сложнее балансить;
- нужен сильный валидатор.

### Рекомендация

Для MVP использовать вариант A:

```text
ручные шаблоны + controlled random внутри слоёв
```

Позже перейти к процедурной генерации регионов.

## 14. Как админка помогает разработке

Первый набор вопросов, на которые админка должна отвечать:

- сколько времени игрок проходит первый рудник;
- на какой минуте он строит первую шахту;
- сколько раз он вручную собирает ресурс до авто-сбора;
- когда открывается первая автоматизация;
- какой ресурс становится bottleneck;
- сколько блоков игрок ломает руками;
- когда игроку становится скучно.

Последний пункт админка сама не почувствует, но хотя бы цифрами намекнёт, где игра начинает вести себя как занудный камень с интерфейсом.
