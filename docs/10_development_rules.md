# Goblin Cartel: правила разработки и итераций

**Версия:** 0.1
**Дата:** 2026-04-28
**Статус:** обязательный рабочий регламент

## 1. Назначение

Этот документ фиксирует правила, которые нужно применять в каждой итерации разработки. Он дополняет проектные документы `00_README.md` - `09_sample_configs.md` и новые требования владельца проекта.

Если этот документ расходится с ранними архитектурными документами, применяется более новое правило из этого файла. Например, для базы данных выбран обязательный стек **Drizzle + drizzle-kit**, хотя в раннем документе backend допускал Prisma или Drizzle.

## 2. Источники контекста

Перед началом новой итерации нужно быстро свериться с:

- `docs/00_README.md` - карта проектных документов;
- `docs/01_game_concept.md` - концепция и продуктовые столпы;

## 3. Протокол каждой итерации

Каждая итерация должна иметь собственную папку:

```text
docs/iterations/0001_name_iteration/
```

Номер всегда четырехзначный и монотонно растет: `0001`, `0002`, `0003`.

Минимальный состав папки:

```text
README.md
```

Рекомендуемый шаблон `README.md`:

```md
# 0001 name iteration

## Цель

## Входной контекст

## Решения

## Сделано

## Измененные файлы

## Проверки

## UTF-8 и текст

## CI/CD и миграции

## Открытые вопросы
```

Правила ведения:

1. В начале итерации создать или обновить папку итерации.
2. Фиксировать фактические решения, а не планы "на потом".
3. Если принято архитектурное решение, указать причину и затронутые файлы.
4. Если проверка не запущена, записать причину.
5. В конце итерации обновить `Сделано`, `Проверки`, `Открытые вопросы`.

## 4. Базовый стек

Клиент:

```text
Vite + React + TypeScript + PixiJS + Capacitor
```

Backend/admin:

```text
Node.js + TypeScript
Fastify или NestJS
PostgreSQL
Drizzle ORM
drizzle-kit для миграций
React + Vite для админки
Zod / JSON Schema для валидации контента
```

Ключевое разделение:

- `game-core` - чистая TypeScript-логика без React и PixiJS;
- игровой UI - React;
- 2D-сцена рудника - PixiJS;
- Android-сборка - Capacitor;
- контент, версии, админка и remote config - backend + PostgreSQL.

## 5. База данных и миграции

Обязательные правила:

1. Использовать PostgreSQL.
2. Использовать **Drizzle ORM** как основной слой доступа к БД.
3. Использовать **drizzle-kit** для генерации и применения миграций.
4. Миграции коммитятся в репозиторий.
5. Изменение схемы без миграции запрещено.
6. Миграции должны запускаться в CI и в CD перед перезапуском backend.
7. Схема БД должна учитывать версионирование контента, админские роли, зашифрованные credentials и аудит важных действий.

## 6. Секреты, env и админка

Базовые runtime-переменные окружения допустимы в `.env`/секретах окружения:

- `BASE_URL` или публичный базовый URL;
- `DATABASE_URL`;
- `APP_CREDENTIALS_MASTER_KEY`;
- `APP_BOOTSTRAP_ADMIN_EMAILS`;
- технические переменные запуска вроде `NODE_ENV`, `PORT`.

Все остальные ключи и интеграционные настройки должны настраиваться в админке и храниться в БД в зашифрованном виде через `APP_CREDENTIALS_MASTER_KEY`.

Примеры того, что не должно жить обычным текстом в `.env` приложения:

- RuStore credentials;
- SMTP/API ключи;
- object storage keys;
- analytics tokens;
- push credentials;
- любые внешние сервисные токены.

Требования к реализации:

1. Мастер-ключ не хранится в БД.
2. Значения credentials в БД шифруются современным AEAD-алгоритмом, например AES-256-GCM.
3. У credentials должны быть имя, тип, окружение, зашифрованное значение, дата обновления и автор изменения.
4. Чтение и изменение credentials должно попадать в audit log.
5. В UI админки секреты не показываются обратно открытым текстом после сохранения.

## 7. Доступ к админке

Bootstrap-доступ задается через:

```text
APP_BOOTSTRAP_ADMIN_EMAILS
```

Правила первого входа:

1. Переменная содержит список email, которым разрешен bootstrap-вход.
2. Первый вход для такого email допускается без пароля.
3. После первого входа пользователь обязан установить пароль.
4. До установки пароля доступ к остальным разделам админки закрыт.
5. После установки пароля passwordless-вход для этого пользователя отключается.
6. Все bootstrap-события логируются.

## 8. UI styles

Единственный обязательный продуктовый источник визуального направления:

```text
docs/08_ui_ux_style_guide.md
```

Правила:

1. Общие UI styles нужно зафиксировать в одном общем файле темы/токенов при первом появлении frontend-кода.
2. Компоненты должны брать цвета, размеры, радиусы, тени и базовую типографику из общего файла, а не дублировать значения локально.
3. Для игрового клиента и админки допускаются разные layout-решения, но базовые токены должны быть согласованы.
4. Основное визуальное направление: `dirty cartoon dark fantasy industrial UI`.
5. UI должен быть mobile-first, читаемым на 360x640 и пригодным для Android WebView.
6. Debug UI разрешен только в dev-режиме и не должен попадать в production.

## 9. Тесты

Unit tests обязательны для каждой логики, где есть правила, формулы или преобразования данных.

Приоритет тестирования:

1. `game-core`: добыча, урон, награды, генерация рудников, офлайн-прогресс, экономика.
2. Валидация контента: схемы, ссылочная целостность, локализация, assetId.
3. Backend: auth, credentials encryption, permissions, content publishing, migrations.
4. UI: критичные состояния и smoke-тесты основных экранов.

Итерация не считается завершенной без:

- запущенных unit tests;
- или явной записи в папке итерации, почему тесты пока невозможно запустить.

## 10. UTF-8 и битые символы

Проект русскоязычный, поэтому текстовые файлы должны храниться в UTF-8.

Обязательные правила:

1. Все `.md`, `.json`, `.ts`, `.tsx`, `.js`, `.css`, `.html`, `.yml`, `.yaml`, `.ps1` хранить как UTF-8.
2. Перед завершением итерации запускать проверку кодировки и типичных mojibake-последовательностей.
3. Проверять отсутствие символа замены `U+FFFD`.
4. Проверять типичные признаки битого текста и mojibake-последовательности, перечисленные в `tools/check-text-encoding.ps1`.
5. При чтении русских файлов в PowerShell использовать UTF-8 вывод, чтобы не спутать проблему консоли с проблемой файла.

Для локальной проверки добавлен скрипт:

```text
tools/check-text-encoding.ps1
```

## 11. CI/CD

Основной репозиторий:

```text
git@github.com:pigrov/goblin-cartel.git
```

Целевой сервер для деплоя:

```text
ssh selectel-transcribe
```

Минимальный CI:

1. install dependencies;
2. lint;
3. typecheck;
4. unit tests;
5. UTF-8/mojibake check;
6. build game client;
7. build admin;
8. build backend;
9. проверка Drizzle migrations.

Минимальный CD:

1. Деплой только после зеленого CI.
2. Подключение к серверу через SSH.
3. Получение новой версии приложения.
4. Установка production-зависимостей или сборка артефакта.
5. Запуск `drizzle-kit` миграций.
6. Перезапуск backend/admin сервиса.
7. Smoke-check health endpoint.
8. Логирование версии деплоя.

CI/CD-секреты для доступа к GitHub и SSH являются инфраструктурными секретами и хранятся в GitHub Actions/серверном окружении. Секреты самого приложения должны идти через зашифрованные credentials в админке, кроме базовых runtime-переменных из раздела 6.

## 12. Документирование изменений

Любая итерация должна оставлять след:

- что было сделано;
- какие файлы изменены;
- какие проверки запущены;
- какие решения приняты;
- какие риски остались;
- что нужно сделать следующим шагом.

Если правило оказалось неудобным или неверным, его можно менять, но только через явную правку этого документа и запись в текущей итерации.
